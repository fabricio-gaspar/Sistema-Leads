## Contratos e decisões explícitas

- Migration CLI: `supabase/migrations/20261005223638_audit_r4_team_access.sql`, criada pelo CLI oficial já disponível (help consultado). Não aplicada a projeto real.
- `team_invite_prepare`, `team_invite_cancel`, `team_invite_accept`, `team_pending_invites` e `team_member_change`: wrappers invoker para corpos privados; PUBLIC/anon sem execute. RPCs usam JWT do **titular**, não service-role nem actor_id fornecido pelo browser. Não confiam em metadata para papel/empresa.
- Prepare/reenvio incrementa revisão; cancelamento vence aceite posterior ou falha honestamente se o aceite já venceu. Aceite duplicado mantém uma associação, sem reativar associação desabilitada. Duas empresas podem convidar a mesma identidade; não há reserva global de e-mail.
- O trigger de Auth preserva onboarding autônomo e dados cadastrais descritivos da empresa nova. Convite cria apenas perfil, nunca associação ativa. A fonte [GoTrue Invite](https://raw.githubusercontent.com/supabase/auth/master/internal/api/invite.go) mostra criação de usuário antes de sendInvite; portanto `invited_at` isolado é insuficiente. O marcador `wayflex_invitation` somente **suprime bootstrap**, inclusive no intervalo cancelamento → criação Auth; não concede qualquer acesso e é seguro mesmo sendo metadata editável.
- E-mail é efeito externo não transacional: falha SMTP mantém convite canônico pendente, devolve `delivery=failed`; conta existente recebe `existing_account` e aceita pela rota autenticada `/convites`. Nenhum usuário Auth é apagado como compensação. O endereço de entrega real e fluxo de confirmação precisam de homologação.
- Canal de vendedor só é enfileirado após aceite. Falha no enqueue não desfaz identidade/aceite; devolve aviso de revisão. Repetição depende da idempotência e fences do R6. Cutoff R4 preserva `operation_id` e revisão da operação incerta, nunca libera retry cego.
- Remoção/disable não revoga sessões globais de outras empresas. JWT previamente emitido não basta: os RPCs e RLS consultam membership atual; mudança de vínculo corta acesso empresarial. Nenhum logout/remoto/provider é executado pelo SQL.
- Vínculos `invited` legados não podem ser habilitados pelo botão de status. Linhas antigas já inconsistentes não são corrigidas automaticamente; administrador emite convite novo/revisionado e titular aceita. Sem migração massiva de dados reais.
- Disponibilidade limita novas concessões/reativações, não revoga retroativamente todos os membros de um papel. Último administrador continua protegido pelo trigger R1. Não inventamos exigência comercial de MFA nem autoridade de dono de plataforma.

## Provas e limites

| Modalidade | Execução | Resultado |

| SQL PGlite 0.3.14 | `teamAccessR4.integration.mjs`, migrations R1+R4 reais, esquema reduzido e dados sintéticos | 47/47; EV-R4-001 |

| Handler HTTP real com dependências simuladas | `runtimeHandlers.test.ts`, sem fetch externo autorizado | 116/116 (arquivo compartilhado, inclui outras áreas) |
| Contrato frontend | `teamMembersRepository.test.ts` | 7/7; inclui revisão explícita, resultado parcial, resposta velha descartada, invalidação e matriz |
| ESLint direcionado | Handler, definições, repositório/teste, duas telas de equipe e gate | Aprovado |
| TSC global | Rodado durante trabalho paralelo | Sem erro R4 observado; consolidação final pelo root |

Os testes concorrentes confirmam: cancelar→aceitar; aceitar→cancelar; indisponibilizar papel→aceitar; desativar gerente→convidar. A segunda operação espera lock; READ COMMITTED reavalia estado, RR/Serializable falham com 40001. No-op UPDATE da organização cria barreira MVCC, não apenas advisory lock.

Fixture reutiliza catálogo/policies/funções da auditoria sem dados pessoais. O root disponibilizou `R4_SCHEMA_READONLY.json` com metadados atuais: confirmou unique(org,email), token com default, actor_name obrigatório e profiles nome/e-mail obrigatórios e e-mail único. SQL inclui actor_name; fixture foi reforçada para esses campos e distingue identidade nova de existente. Suportes reduzidos não representam snapshot completo de produção. Não houve login/MFA/SMTP real, aceite por e-mail real, teste browser ponta a ponta, aplicação remota, integração com gateway real ou garantia de prontidão comercial. RLS rejeita membership inativa, mas esta frente não testou revogação criptográfica de JWT (nem a alega).
