## Delta e contratos

`sessionContext` é apenas a barreira de dados no navegador, não uma nova autoridade de autorização. O snapshot é imutável `{userId, organizationId, generation}`; cada transição cria uma geração. `resolveOrganizationSession` continua consultando Auth, perfil e vínculo ativo. Verifica a geração depois de cada await. Se descobrir outra organização, atualiza o contexto para a leitura canônica, mas **aborta o chamador antigo**, sem usar seu payload na nova empresa. `switchOrganization` limpa primeiro e só então executa a RPC canônica.

`createContextStore` substitui a repetição de singletons em Leads, Listas, Conversas, Catálogo, Tarefas, Propostas, Fluxos, EmpresaSettings, Compromissos, TemplatesProposta, Fontes e Integrações. Os contratos públicos dos hooks existentes são preservados. A store limpa dados, erro, carregamento e fila na mudança de contexto; rejeita editar antes de leitura confirmada; callbacks de escrita ficam presos à geração do render. Leitura anterior a uma alteração otimista não desfaz a alteração. Falha de gravação continua sendo falha após releitura canônica.

`createBackendStore` reutiliza a mesma barreira para seus consumidores legados. Não lê localStorage operacional, não salva cópia operacional no navegador, não semeia automaticamente um backend vazio, não inscreve um listener Auth por módulo. A antiga escrita de configuração no import foi removida. A assinatura é mantida e defaults estruturais de objetos são mesclados **somente na leitura**. Dados empresariais vazios não herdam WayFlex, preços/descontos ou mídias fictícias; exemplos de templates de proposta continuam disponíveis como constantes editoriais, sem persistência automática.

As filas relacionais receberam guards antes das próximas mutações em leads, listas/vínculos, tarefas, conversas, sequências/passos, catálogo, propostas e configurações. Propostas capturam uma sessão para o lote inteiro, em vez de resolver outra organização para cada item. Não foi criada operação remota nova.

Auth tem um único observer. Eventos são tratados sincronamente; consultas Supabase posteriores ficam fora do callback Auth. `getSession` inicial atrasado não restaura A depois de um evento B. Logout limpa o contexto antes de esperar a rede e eventos autenticados atrasados não desfazem a intenção explícita de sair. O `AuthProvider` remonta filhos pela geração, removendo também estados React locais, timers/subscriptions vinculados às telas e QR/códigos transitórios.

`currentAccess` deixa de usar apenas userId e cache indefinido. Invalidação explícita também rejeita a promessa antiga ainda em andamento; `useCurrentAccess` não oferece a permissão da revisão anterior. Diagnóstico e listagem de contas não emprestam uma requisição em andamento para outra empresa.

Preferências em `useLocalStorageState` recebem prefixo por usuário/organização (sem ler o namespace global antigo); podem sobreviver a uma nova geração do mesmo contexto porque são preferências, não fonte operacional. A chave da tentativa idempotente de Busca também é particionada por usuário/empresa. Nenhum filtro ou resposta de cliente é transmitido no sinal entre abas.

## Integração R4

O aceite cego `activate_invite` no login foi removido. `OrganizationGate` usa `PendingInvitesGate` fornecido pelo lote R4 quando não há organização válida; `/convites` e o link no menu de perfil permitem aceite explícito também para quem já pertence a outra empresa. Após aceite, `refreshOrganization` invalida e resolve o contexto novamente.

Provisionamento/seed de empresa pelo frontend também foram removidos. O cadastro fornece os dados declarativos a Supabase Auth; o trigger canônico do R4 cria a empresa própria ou mantém convidado pendente sem vínculo ativo. **Não publicar R5 sem a migração/backend R4 compatíveis.** Nenhum papel/tenant é escolhido por metadata editável no frontend.

### Correções adicionais da revisão independente

- T-R5-034/035 exercitam as duas opções optimistic. Updaters só são calculados no início efetivo da execução serial, sobre o último valor canônico confirmado. Falha de uma escrita invalida o mutationEpoch: operações já enfileiradas não calculam seu updater nem gravam payload derivado da falha. Releitura reconcilia possíveis efeitos parciais, mantém o erro e exige refresh explícito antes de uma nova tentativa humana.
- T-R5-036 reproduz logout pendente + sinal refresh de outra aba. Esse sinal não desfaz a intenção explícita de logout nem restaura a sessão SDK ainda viva.
- T-R5-037 reproduz leitura iniciada durante save que retorna depois do acknowledgement. O acknowledgement invalida essa leitura pré-gravação; ela não sobrescreve o canônico confirmado.
- T-R5-038/039 usam o adapter real TemplatesProposta. Edições parciais/adição/cópia/exclusão/default passam o cálculo para dentro da fila; um template removido por uma operação anterior não pode virar padrão por callback enfileirado. Outros adapters foram revistos: Fontes usa store.get apenas para localizar o alvo de um comando explícito enabled, não para montar um replacement parcial de todo o estado.
- Root e security reproduziram/revisaram esses casos. `REVISAO_R5_R11.md` preserva a revisão independente. Teste legado de Listas agora exige o refresh explícito do novo contrato; não foi convertido em sucesso silencioso após falha.

Os históricos T-UI-006/007 agora têm regressões T-R5-021/022 usando os hooks/stores reais com repositories sintéticos; T-UI-008 tem regressão T-R5-012 usando `createBackendStore` real e interceptando qualquer tentativa de upsert. Provas adicionais exercitam promises fora de ordem, A→B, usuário igual/empresa diferente, empresa igual/usuário diferente, logout/relogin igual, fila suspensa, setters antigos, erro tardio, cache/TTL/invalidação, sessão inicial atrasada e dois transports de abas independentes. Sem rede e sem clientes.

## Limites e revisão

- Não houve E2E visual com duas contas ou dois navegadores reais; os dois hosts de StorageEvent são sintéticos e não provam comportamento de permissões de storage em todos os navegadores. Se storage estiver bloqueado, o broadcast Auth do Supabase continua independente; troca de org entre abas nesse ambiente exige homologação/fallback específico.
- Não se pode desfazer uma requisição já aceita pelo servidor antes do corte no navegador. Guards bloqueiam continuação local/novo envio da fila; RLS e autorização backend seguem obrigatórios. Este lote não alega tornar toda mutação multietapa atômica.
- Trocas de geração descartam rascunhos React locais, deliberadamente, para não carregá-los para outra identidade. Eventos Auth que reconfirmam a sessão podem recarregar a tela; validar a experiência no E2E integrado.
- `lib/store.ts` não possui consumidores atuais (`createExternalStore` apenas declarado). Não foi convertido nem usado como fonte operacional.
- A suíte completa foi iniciada apenas como diagnóstico durante alterações concorrentes R4/R6; falhas de contratos desses lotes não foram escondidas nem alteradas aqui. A validação geral final/build pertence ao integrador após congelar fontes.
- Sem commit, push, deploy, SQL remoto, mensagem real, QR operacional ou alteração de dados de clientes. `pnpm-lock.yaml`/`pnpm-workspace.yaml` preexistentes preservados. Checkpoint `.agent`/continuidade permanece com o agente principal.
